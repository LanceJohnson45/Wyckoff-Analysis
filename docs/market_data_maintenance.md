## 旧任务为什么成功、股票却未更新

证据来自 [CN 任务 38869691489](https://github.com/LanceJohnson45/Wyckoff-Analysis/actions/runs/38869691489)、本地已同步行情及当前股票名单。

- 旧 CN 任务维护的是策略池：主板和创业板，排除 ST。该次实际选中 4,397 只，并非行情库中的全部 A 股。
- 旧退出条件为 `ok > 0 or fail == 0`，所以 4,373 成功、24 失败仍返回 0。部分补齐也曾计入成功。
- 每只股票独立计算截止日；任务从上海时间 15:50 跑到 16:23，跨过 16 点切换，使同批股票分别以 10 月 15 日和 16 日为目标。
- 新上市股票先补上市前的旧缺口，失败就中断，导致最新数据也没有机会更新。例：001257 的失败窗口截至 2026-03-30，而 Yahoo 明确的首次交易日是 2026-03-31。
- BaoStock 将正常空数据也累计为连接故障，可能让其他股票的备用源进入熔断。
- Git checkout 会刷新名单缓存文件的 mtime，旧的文件年龄判断不能保证每日取得最新证券名单。

- 上市边界采用人工公告日期，或 Yahoo 明确的 `firstTradeDate` 元数据。不会把缓存的第一根 K 线、空返回或 `possibly delisted` 当作退市证据。

- 网络故障、未知空数据、停牌待核实、剩余交易日缺口，继续保留在审核表。正常无成交不累计为 BaoStock 网络熔断。
- 有失败、部分补齐或名单刷新警告时，预热返回 **2**，Action 失败；正常完成返回 0。只读 `--dry-run` 返回 0 不代表已经补齐。
- 检查点带验证版本与规则指纹，旧版“完成”状态重新核验；强制重跑失败会清除旧 ready 标记，包括多次检查点保存后的情况。
- CN/US Action 使用 Python 3.12 与 `uv sync --frozen --no-dev`，依赖由 `uv.lock` 固定。

这里的“完成”沿用项目的近期补缺设置 `FUNNEL_PREWARM_RECENT_GAP_MAX_AGE_DAYS`（默认 45 个自然日）。有历史缓存时可忽略更早的缺口，不能据此宣称历史每一天都完整。若要核验整个请求窗口，将该值设为 0；停牌日不会制造 K 线，仍需人工核实。

## 审核列表与维护方式

每轮产生 `logs/prewarm_<market>_<目标日>_review.csv`、`_coverage.csv`、`_summary.json`：

- review：失败、部分补齐、未执行完和只读模式缺口。
- coverage：全部本轮股票，包括排除项、已完成项及最新日期。
- summary：各状态数量、目标日、名单警告和带 +08:00 的生成时间。

初始即写待处理清单，每 100 只保存一次，结束时保存最终结果。超时可能保留最近检查点而非每只股票的最终状态；重跑会继续核验。Actions 的 Summary 展示统计，Artifacts 中下载这些 CSV/JSON（保留 7 天），失败或超时也尝试上传。空名单或初始化阶段直接失败时，可能只有控制台错误。

审核时先核对 `target_date/latest_date/missing_ranges/detail`；确认退市、合并或代码变化后才维护 JSON 的 `exclude/reason/effective_from/evidence`。新股可填写 `listing_date/evidence`。不需要删除行情库历史；普通网络故障应重跑，不加入排除名单。

本次已生成的历史产物在 `logs/prewarm_original_run_38869691489/`：29 行审核表，以及 830 行落后库存明细。后者包含策略池外股票，不应全部视作退市名单。

只读核验示例（读取已配置行情库，不拉取或写入日线）：

```bash
uv run --frozen --no-dev python scripts/funnel_prewarm.py \
  --market cn --symbols 000004,001237,001248,001257,301666 \
  --end-date 2026-10-15 --dry-run --review-dir logs/prewarm_readonly_validation
```

`--force` 会忽略当日完成检查点；去掉 `--dry-run` 则会实际拉取并写入已配置行情库。
