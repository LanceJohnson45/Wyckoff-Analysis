# 日线预热超时与续跑

CN Daily Market Data 的预热采用以下预算（从预热脚本启动计时，包含准备阶段）：

| 层级 | 默认值 | 到期行为 |
|---|---:|---|
| 单票总时限 | 60 秒 | 终止该执行进程，必要时强杀；其他股票继续 |
| 停止派发 | 60 分钟 | 队列剩余股票保存为 pending |
| 结束在途任务 | 65 分钟 | 终止剩余执行进程，保存检查点及审核产物 |
| shell 最后保护 | 70 分钟 | GNU timeout，30 秒后升级强杀 |

正常股票复用 spawn 子进程，避免每票重新加载依赖，也避免继承父进程的数据库连接。TickFlow 的请求间隔由父进程统一分配；子进程被终止后不会留下共享限频锁。

名单、交易窗口和交易日历准备各有最多 180 秒的独立进程时限，停复牌查询最多 30 秒，且都受剩余批次预算约束。准备阶段失败仍报错；缺少停牌证据时不能免补日线。

脚本参数：

```bash
uv run --frozen --no-dev python3.12 scripts/funnel_prewarm.py \
  --market cn --universe all --trading-days 320 \
  --symbol-timeout-seconds 60 \
  --dispatch-budget-seconds 3600 \
  --run-budget-seconds 3900
```

未显式传预算时，根据已有 `FUNNEL_PREWARM_TIMEOUT_MINUTES` 提前 10 分钟停止派发、提前 5 分钟结束在途任务；因此 US 的 45 分钟外层保护对应 35/40 分钟内部预算。`--sleep-seconds` 控制派发间隔，等待期间仍监督单票超时。

审核产物中的 `symbol_timeout` 表示该进程已被回收；`pending / batch_deadline` 表示本轮未能完成，下轮重新核验。确认全天停牌的股票单独标记 `suspended`，后续运行重新查询复牌状态。

保持缓存并以正常模式启动使用新提交的工作流；已确认就绪的同日股票复用检查点，超时或 pending 股票不会被标为就绪。进程在写入后超时的股票也会重新读缓存核验，不能凭不完整结果宣称成功。

有失败、缺口或 pending 时退出码仍为 2；这是已保存审核结果的未完成状态。外层退出码 124 仍表示最后保护超时，不能作为成功处理。现有工作流会继续尝试指数更新并保存缓存、上传产物。

验证覆盖真实进程卡死及强杀、后续任务继续、停止派发、在途终止、派发间隔不阻塞监督、跨进程限频、检查点保存及续跑。完整 GitHub 网络和云端写入耗时须由新工作流运行验证。

## 2026-10-21 首次实际验证

[运行 #126](https://github.com/LanceJohnson45/Wyckoff-Analysis/actions/runs/39586386370) 使用提交 `790a3458`，作业耗时 16 分 3 秒。预热返回 2，统计为 ok=5540、fail=0、partial=35、deferred=0，其中 8 只全天停牌正确处理；指数更新 364 根，检查点和审核产物均已上传，未触发外层超时。

最新名单纳入了此前遗漏的新股，首次真实运行暴露出两类边界问题：北交所报价没有上市日期元数据，以及 Yahoo 能返回有缺口的日线却被当作成功，未继续切源。补正为按北交所、深交所正式名单读取上市日期并保存证据；维护入口对已明确边界的请求传递必需交易日，任一必需日期缺失或 OHLCV 无效都会继续切源。首次未知上市日期的冷启动仍允许读取源元数据，不能拿行情最早日期直接推断上市日。

对上述 35 只只读复核，校准边界后 30 只已有缓存满足近期验收；另 5 只仍需补齐真实历史缺口，继续保留审核。该复核不写云端，也不替代补正后的实际工作流验证。

## 数据源与定时调度诊断

CN 工作流开启 `DATA_SOURCE_DEBUG=1`。`data_source_request/attempt/returned/failure/rejected/selected` 通过 `request_id` 关联同一标的和区间：`returned` 只代表源返回，`selected` 才代表通过交易日覆盖核验。`rejected` 会记录缺失日期；`failure` 记录错误类别，不输出可能带鉴权信息的上游异常原文。`elapsed_ms` 为来源请求或整体选择耗时，`prewarm rate_limit` 单独记录 TickFlow 排队秒数。`prewarm fetched` 在写库前记录实际命中源与行数；它不代表写库完成。

CN 定时任务先检查 `market_data_schedule` 日志中的北京时间和 `target_date`。目标日按既有收盘切日规则确定：周六凌晨延迟执行的周五任务仍可补周五数据；目标为周末或交易日历中的节假日时跳过个股和指数拉取。日历不覆盖目标日或加载失败时明确报错。手动触发保留补数能力，不因周末而跳过。预热使用检查步骤输出的固定目标日，避免排队或跨午夜改变更新日期。

该改动用于查明吞吐瓶颈，保留现有来源顺序、限频和未完成退出码。上线后须根据 `selected` 的来源统计和 `rate_limit` 等待记录确认瓶颈，不能仅凭完成间隔认定所有请求都命中 TickFlow。
